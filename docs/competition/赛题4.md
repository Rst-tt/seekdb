# 赛题四：全文索引调优

| 项目 | 说明 |
| --- | --- |
| 项目 | seekdb |
| 题目 | 全文索引性能优化 |
| 任务 | 优化全文索引构建、分词和查询链路，在保证结果正确的前提下降低耗时 |
| 性能评分 | 满分 100 分，三类指标等权计分，综合耗时下降 50% 达到满分 |
| 总分 | 50 分 |


## 一、题目背景
全文索引为数据库提供文本检索能力。随着文档数量和文本长度增加，分词、排序、倒排结构生成和数据写入会带来较大的 CPU、内存与 I/O 开销，影响索引构建效率和查询响应时间。

本题要求分析 seekdb 全文索引的性能瓶颈，完成数据库内核优化，并通过统一基准测试验证效果。优化应保持原有分词与检索语义，兼顾索引构建、分词和查询的整体表现。

## 二、题目内容
### 2.1 定位瓶颈并完成优化
参赛者可选择一个或多个方向开展优化，不要求实现全部方向：

| 优化方向 | 可研究的问题 |
| --- | --- |
| 分词热路径 | 减少逐字符处理、重复函数调用、临时对象创建和内存分配开销 |
| 排序与归并 | 优化排序键比较、批量排序、外部归并及中间数据读写 |
| 索引构建流程 | 改善任务划分、并行执行、流水线衔接和数据分发效率 |
| 内存与 I/O | 复用解析器和缓冲区，优化内存使用与落盘策略 |
| 全文查询 | 减少倒排访问、结果合并和查询执行中的重复工作 |


需说明瓶颈定位依据、主要修改及其影响，并提供优化前后的性能对比。不能通过减少输入数据、跳过必要处理、改变分词规则或硬编码测试结果获得性能提升。

### 2.2 保证功能正确
优化后应能正常构建全文索引，保持 TOKENIZE 分词结果及 MATCH 查询语义正确。涉及共享排序、内存管理或存储路径的修改，应验证相关功能没有回归。

基准中的查询命中数量是核对结果的辅助信息，不能替代完整的正确性验证。针对修改点补充必要的回归用例，避免只验证耗时而忽略结果。

## 三、测试方法与评分
### 3.1 统一测试流程
已有 VLDB CI 会编译并启动 seekdb，运行全文索引基准测试，再根据固定基线生成性能报告和分数。全文索引评测涉及的主要文件如下：

| 文件 | 用途 |
| --- | --- |
| `.github/workflows/vldb.yml` | CI 编译、启动和评测入口 |
| `tools/benchmark/fts_large_bench.sh` | 执行数据导入、索引构建、分词和查询测试 |
| `tools/benchmark/fts_large_bench_gen.py` | 生成测试数据 |
| `tools/benchmark/fts_large_bench_setup.sql` | 初始化测试库表 |
| `tools/benchmark/fts_large_bench_score.py` | 根据报告计算分数 |
| `tools/benchmark/fts_large_bench_baseline.json` | 固定测试参数、基线指标和评分规则 |


默认测试包含 20,000 篇中英文文档，每批导入 500 行；分词每组执行 3,000 次，每条查询每组执行 200 次。分词与查询各采样 3 组、每项预热 30 次。完整评测使用 `SKIP_LOAD=0`，包含重新导入数据和构建索引。

### 3.2 计分指标
| 类别 | 测试内容 | 指标 |
| --- | --- | --- |
| 索引构建 | IK 标题与正文索引、IK 正文索引、BENG 英文标题与正文索引 | `build_ik_all_sec`、`build_ik_content_sec`、`build_beng_en_sec` |
| 分词 | IK 中文分词、BENG 英文分词 | `tokenize_ik_avg_ms`、`tokenize_beng_avg_ms` |
| 查询 | 中文、英文、中英文混合、带 LIMIT 的全文查询 | `query_cn_avg_ms`、`query_beng_avg_ms`、`query_mixed_avg_ms`、`query_limit_avg_ms` |


以上指标均为耗时，越低越好。分词与查询使用各采样组“总耗时 ÷ 执行次数”的平均值计分。SELECT 1 耗时、原始数据导入速度、索引构建总耗时和查询命中数量用于辅助分析，不直接参与性能评分。

### 3.3 评分规则
对每项指标计算耗时下降比例：

**单项提升率 =（基线耗时 − 提交版本耗时）÷ 基线耗时**

先分别计算构建、分词、查询三类内部各指标提升率的算术平均值，再对三类结果等权平均：

**综合提升率 =（构建平均提升率 + 分词平均提升率 + 查询平均提升率）÷ 3**

**性能得分 = 100 × min(max(综合提升率, 0), 0.5) ÷ 0.5**

例如，三类平均提升率分别为 40%、30%、20%，综合提升率为 30%，得分为 60 分；综合提升率达到 50% 时得满分。这里的 50% 指耗时减半，不是“速度提高 50%”。

某项退化会以负提升率参与平均，不会在单项层面截断为零。三类等权，不是将全部 9 项指标直接平均。

正式成绩以统一评测环境和固定基线为准。参数不一致或报告缺少计分指标时，评分脚本会拒绝计算；不能修改测试数据、SQL、计时逻辑、评分脚本或基线来提高分数。

功能正确是性能成绩有效的前提。现有性能脚本会记录查询命中数量，但评分函数主要根据耗时计算分数，需结合回归测试及结果核对验证正确性，不能仅凭性能分数认定功能通过。

### 3.4 本地复现
准备好已启动的 seekdb、MySQL 兼容客户端、Bash 和 Python 3 后，在 seekdb 仓库根目录运行：

```bash
export MYSQL='mysql -h127.0.0.1 -P2881 -uroot -N -s -A --default-character-set=utf8mb4'
export MYSQL_VERBOSE='mysql -h127.0.0.1 -P2881 -uroot -A --default-character-set=utf8mb4'

REPORT_FILE=$(mktemp /tmp/fts-bench-report.XXXXXX)
LABEL=local ROWS=20000 BATCH=500 ROUNDS=3000 QUERY_ROUNDS=200 \
  SAMPLES=3 WARMUP=30 SKIP_LOAD=0 OUTPUT="$REPORT_FILE" \
  bash tools/benchmark/fts_large_bench.sh

python3 tools/benchmark/fts_large_bench_score.py "$REPORT_FILE"
```

按实际环境调整客户端和连接参数。脚本会删除并重建 `fts_large_bench` 测试库，应在专用测试实例运行。报告以追加方式写入文件，每次完整测试应使用新文件。

对比优化前后版本时，保持硬件、资源配置、编译方式、测试参数和机器负载一致。可重复运行观察波动；本地机器与 CI 环境不同，使用 CI 固定基线计算的本地分数仅供参考。
